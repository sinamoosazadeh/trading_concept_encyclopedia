# Review checklist

Use this checklist for substantive concept or claim changes. Mark items as pass, fail, not applicable with rationale, or not yet checked in the review record. A checked box is not proof by itself; reviewers should be able to point to the evidence.

## A. Identity and ontology

- [ ] The record is not an accidental duplicate of an existing canonical entry.
- [ ] Canonical name, aliases, spelling variants, language, and context are explicit.
- [ ] The concept is correctly classified as an observation, pattern, indicator, feature, hypothesis, signal, setup, strategy, execution method, or control.
- [ ] Relationships use directional semantics correctly and explain their rationale.
- [ ] Related or confused terms are distinguished without collapsing meaningful differences.

## B. Definition quality

- [ ] The definition is neutral and understandable without promotional language.
- [ ] Descriptive definition is separated from hypotheses and performance claims.
- [ ] Necessary preconditions, inputs, parameters, timeframes, and decision timing are recorded.
- [ ] Observable criteria are measurable or discretionary judgement is explicitly identified.
- [ ] Start, confirmation, invalidation, reset, and edge cases are defined when applicable.
- [ ] Any ambiguity between wick, close, intrabar observation, or bar-close confirmation is resolved or disclosed.
- [ ] Known variants are represented rather than silently forced into one universal definition.

## C. Source and claim integrity

- [ ] Each material factual claim is atomic and scoped.
- [ ] Supporting sources directly support the statement being made.
- [ ] Contrary, null, or conflicting evidence has been sought and recorded.
- [ ] Source edition, provenance, publication/access dates, and relevance notes are adequate.
- [ ] Missing or uncertain bibliographic information is not fabricated.
- [ ] Claim status does not exceed the evidence.
- [ ] Source rights and quotation limits have been considered.

## D. Operational and data integrity

- [ ] A claimed mechanical rule can be implemented from available-at-time data.
- [ ] Future-bar dependence and repainting behavior are documented.
- [ ] Timezones, timestamps, resampling, and data revisions are specified where relevant.
- [ ] Missing values, duplicate events, warm-up periods, and contract/symbol changes have explicit behavior.
- [ ] Data leakage and target contamination have been assessed.

## E. Empirical claims

- [ ] Hypothesis and primary outcome were specified before confirmatory testing.
- [ ] Asset, venue, timeframe, date range, and sample-selection rules are disclosed.
- [ ] Baseline and benchmark are meaningful.
- [ ] Fees, spread, slippage, funding, latency, liquidity, and fill assumptions are reasonable for the claim.
- [ ] Look-ahead, survivorship, selection, multiple-testing, and regime risks are addressed.
- [ ] Out-of-sample results are separated from exploratory selection.
- [ ] Uncertainty, denominator, sample size, drawdown, and relevant risk metrics are reported.
- [ ] Null results, failures, and deviations from protocol are preserved.
- [ ] The conclusion is restricted to the tested scope.

## F. Machine and repository integrity

- [ ] Stable ID and filename agree.
- [ ] JSON Schema validation passes.
- [ ] Source and related-concept references resolve.
- [ ] Vocabulary values match the controlled registry.
- [ ] Duplicate IDs or unintended alias collisions are absent or explained.
- [ ] Automated tests and report generation pass.
- [ ] Changelog, migration, or release notes are updated where required.

## G. Release judgement

- [ ] Remaining limitations and unresolved questions are visible.
- [ ] Editorial status and evidence status are independently justified.
- [ ] Reviewer can distinguish a complete definition from an unvalidated trading hypothesis.
- [ ] Release statement does not imply comprehensive coverage or profitability without evidence.
