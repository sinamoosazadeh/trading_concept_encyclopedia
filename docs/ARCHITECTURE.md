# Repository architecture

## Architectural objective

The repository separates the human knowledge model, machine-readable records, validation rules, derived reports, and published research claims. The primary artifact is a version-controlled set of canonical records; reports are derived artifacts and must never become the sole source of truth.

## Layers

1. **Editorial policy** — scope, ontology, evidence policy, terminology, review rules, licensing, and governance.
2. **Canonical data** — concept entries, claim records embedded in concepts, source registry, taxonomies, and controlled vocabularies.
3. **Contracts** — JSON Schemas define required fields, value types, allowed enum values, and local structural constraints.
4. **Integrity validation** — scripts validate JSON, schemas, identifiers, file-path consistency, source and relationship references, duplicate IDs, and vocabulary consistency.
5. **Derived views** — deterministic reports expose coverage gaps and metadata counts. Reports are reproducible outputs, not hand-edited data.
6. **Continuous integration** — automated tests and validation run for proposed changes.
7. **Release and migration** — versioned standards and documented migrations preserve compatibility and traceability.

## Canonical versus derived data

Canonical records are stored under `entries/`, source metadata under `sources/`, and vocabulary definitions under `registry/`. Schemas under `schema/` define machine contracts. The output under `reports/` should be generated by scripts; avoid editing it manually. Derived output should state its generation method and never imply that an automated count is a qualitative review.

## Validation is not truth verification

Schema validation can detect missing fields, invalid enums, malformed identifiers, and broken local references. It cannot determine whether a definition is historically accurate, a source is methodologically sound, or a strategy is profitable. Those require editorial and evidence review. The documentation and CLI must keep this boundary explicit.

## Dependency policy

The core data model should remain readable without installing Python packages. Validation dependencies are development tooling, not a requirement for understanding records. Dependencies should be minimal, explicitly declared, and upgraded with tests and release notes. Do not add a heavy search/database stack until an actual use case justifies the complexity.

## Repository operations

- Work in focused branches for material changes.
- Prefer coherent commits that explain why a change exists.
- Run tests and repository validation before requesting review.
- Use pull requests for significant schema, policy, tooling, or bulk-content changes.
- Do not force-push shared history without a documented recovery need.
- Preserve original source snapshots only when permitted by license and policy; otherwise store bibliographic metadata and notes.
